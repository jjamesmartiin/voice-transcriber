# Known limitations and verification log

This is the project's engineering log, kept in the open rather than in a private
notebook. It records two things: **what is verified on which platform** (and,
just as importantly, what is *not*), and the open gaps with the evidence behind
them.

Read it when you want to know how much to trust a claim. Several entries say
exactly what has and has not been proven — "verified end-to-end on Linux,
expected but unconfirmed on macOS, unreachable on native Windows" — and say why.
That honesty is deliberate: a feature that is unverified on your platform is
different from one that is broken, and you deserve to be able to tell which you
are looking at before you file an issue.

`- [x]` items are kept for the record of *how* something was validated, not as a
changelog; see [`CHANGELOG.md`](CHANGELOG.md) for what shipped in each release.

own resumable task list: [`TODO-parity.md`](TODO-parity.md). This file stays what it is — the
limitations and verification log.

- [x] **Native Windows has no control API, and no ratatui frontend.** `control.socket_supported()` is `hasattr(socket, "AF_UNIX")`, and **stock CPython on Windows never exposes `AF_UNIX`** — the OS has supported it since Windows 10 1803, but CPython's PR ([bpo-33408](https://bugs.python.org/issue33408)) is still unmerged. Consequences on a native Windows host: the engine does not bind the control socket (`src/main.py` records this at *debug* level only), every `python src/main.py <verb>` fails with `✗ AF_UNIX sockets are unavailable on this platform`, and `tui_ratatui.tui_available()` returns False so the ratatui frontend is disabled and the Rich TUI is used instead. Linux and WSL are unaffected (WSL runs a Linux interpreter). The shared suite now skips its socket tests on such an interpreter and pins the degradation on every platform in `tests/shared/test_control.py::TestUnsupportedTransport`; `docs/control_api.md`, `README.md` and `AGENTS.md` state the limitation. To close it, add a non-AF_UNIX transport for Windows — realistically **TCP on 127.0.0.1** with a per-user port and a token file in `tempfile.gettempdir()` (stdlib only, so the model-free shared tests keep working), or `\\.\pipe\vt-control-<user>` via pywin32 (new dependency, and it would not run in CI). Needs a design decision before implementation.
  - **Fixed for the control API; the ratatui frontend is still Unix-only by design.** There is now a second transport: when `socket.AF_UNIX` is absent the engine binds loopback TCP on `127.0.0.1` with an OS-assigned port, requires a per-run token on every request (constant-time compare; a mismatch says only `unauthorized`), and publishes host/port/token to a `0600` per-user endpoint file that it removes on clean shutdown. `send_command` falls back to TCP automatically when there is no unix socket but a published endpoint exists, so a WSL client can drive a Windows engine. The verbs, framing and reply shapes are unchanged — the transport is the only difference, and `VT_CONTROL_TRANSPORT=unix|tcp` forces one. Tests: `TestTransportSelection` and `TestTcpTransport` in `tests/shared/test_control.py` (real loopback sockets, so they run on every platform, not just Windows), including that it binds loopback only, that the endpoint file is owner-only, and that the token never reaches the engine. **Not verified on a real Windows host** — the AF_UNIX-absent path is simulated by patching `unix_sockets_supported`. The `tui-rs` crate still imports `std::os::unix`, so native Windows keeps the Rich TUI; that part of the original note stands.

Add a matrix job on an arm64 GitHub runner once `nixpkgs` `torch` builds for `aarch64-linux` (it is limited on arm); verify `nix build --system aarch64-linux .#default` under binfmt before wiring CI. The flake already lists `aarch64-linux` in `supportedSystems` and the runtime code is arch-neutral.
- [ ] **macOS packaging (`.app` / `.dmg`).** macOS is source-only (Nix or Homebrew) — there is no AppImage path (nix-appimage is Linux-only). Add a macOS runner + a bundler (PyInstaller onedir wrapped in a `.app`, or a Nix-based macOS bundler), then document it as the end-user macOS download.
- [ ] **CUDA-enabled AppImage / flake variant.** The bundled `torch` is CPU-only, so the AppImage ignores an NVIDIA GPU. Add a `packages.cuda` output (CUDA-enabled torch) with an explicit host-driver requirement, then document the choice. Until then the README states the AppImage is CPU-only.
- [ ] **FUSE-less AppImage UX.** Type-2 AppImages need FUSE 2; document `--appimage-extract-and-run` / `APPIMAGE_EXTRACT_AND_RUN=1` (done in README) and consider a runtime that self-extracts when `libfuse2` is absent, so a double-click works on FUSE-3-only distros.
- [x] **Verify the AppImage model-bundle lookup on a real AppImage.** `src/model_download._local_model_source()` now also checks `dirname($APPIMAGE)/model-bundle` and `$APPDIR/model-bundle` (unit-tested in `tests/shared/test_model_download.py`), but the `$APPIMAGE`/`$APPDIR` values only exist inside a running AppImage — confirm on a built `vt-x86_64.AppImage` with a `model-bundle/` beside it.
  - **Fixed / verified 2026-10-07 on a real built AppImage.** `./scripts/build.sh --bundle` produced `vt.AppImage` (a symlink into the Nix store; 1.18 GB, sha256 `66460b94...`), and the AppImage runtime genuinely exports `$APPIMAGE` and `$APPDIR` — confirmed from inside the running bundle, not assumed. With a *structurally valid stub* bundle (a tar of the five `_REQUIRED_LOCAL` files split into two raw parts, each `xz`-compressed, plus a correctly-formatted `SHA256SUMS`) placed in `model-bundle/` beside the `.AppImage`, and run from a different working directory so only `dirname($APPIMAGE)` could match, `_local_model_source()` resolved it and the engine verified both parts, decompressed, concatenated, extracted and installed with `source_kind="local"` — with no network access. The bundled `model_download.py` is byte-identical to the repo source. Two caveats: the run used `--appimage-extract-and-run` (this host has no `libfuse2`), and the real 2.8 GB weights were never downloaded — the one failure was the hard-coded real-weights `model.safetensors` hash correctly rejecting the stub, which is the gate working as designed.
    - **Incidental finding, not a code bug:** when the AppImage is invoked *through a symlink* — which is exactly what `nix bundle` emits locally — the runtime resolves `$APPIMAGE` to the real target path, so a `model-bundle/` beside the symlink is not found. The asset attached to a release is a real file, so users are unaffected; there is no clean fix from `$APPIMAGE` alone.
    - **Second incidental finding, real and fixed:** the verification crashed on the Rich-TUI path with `TypeError: set_config_state() got an unexpected keyword argument 'hotkeys'` — see the entry below. It is the native-Windows default frontend, so this was a startup crash for every Windows user.
