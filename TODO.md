- [ ] **Native Windows has no control API, and no ratatui frontend.** `control.socket_supported()` is `hasattr(socket, "AF_UNIX")`, and **stock CPython on Windows never exposes `AF_UNIX`** — the OS has supported it since Windows 10 1803, but CPython's PR ([bpo-33408](https://bugs.python.org/issue33408)) is still unmerged. Consequences on a native Windows host: the engine does not bind the control socket (`src/main.py` records this at *debug* level only), every `python src/main.py <verb>` fails with `✗ AF_UNIX sockets are unavailable on this platform`, and `tui_ratatui.tui_available()` returns False so the ratatui frontend is disabled and the Rich TUI is used instead. Linux and WSL are unaffected (WSL runs a Linux interpreter). The shared suite now skips its socket tests on such an interpreter and pins the degradation on every platform in `tests/shared/test_control.py::TestUnsupportedTransport`; `docs/control_api.md`, `README.md` and `AGENTS.md` state the limitation. To close it, add a non-AF_UNIX transport for Windows — realistically **TCP on 127.0.0.1** with a per-user port and a token file in `tempfile.gettempdir()` (stdlib only, so the model-free shared tests keep working), or `\\.\pipe\vt-control-<user>` via pywin32 (new dependency, and it would not run in CI). Needs a design decision before implementation.

- [ ] **Multi-device mic levels (mic picker): Linux/WSL verified, macOS expected-but-unconfirmed, Windows unreachable.** The picker meters *every visible row at once* — `RatatuiTui.start_mic_monitor(indices)` opens one `sd.InputStream` per visible device (bounded to ~11 by the popup's list height), diffs the set on scroll/filter instead of restarting every stream, gives each device a 16 kHz → `default_samplerate` fallback, and skips any device that refuses to open; it publishes `{"t":"vu","level":…,"levels":[{"i":<index>,"level":…}]}`, the Rust side keeps a per-index map (`app.vu_levels`), and `mic_picker.rs` derives the monitored set from the rendered window so metering can never drift from what is on screen. **Verified end-to-end on Linux, in a real terminal.** A tmux-driven harness (real Python bridge + real `vt-tui` binary on an isolated `vt-tui-*.sock`, no engine/model/hotkeys, so it cannot disturb a live instance) opened all 5 input devices at once and rendered 8 consecutive frames with the internal DMIC row reading 57% → 53% → 52% → 48% → 45% → 51% while the other four rows stayed at 0% — exactly the diagnostic the feature exists for. Rust asked for precisely `indices:[9,8,4,5,6]` once and stopped once, so the set-diff works, and Esc returned to the settings modal with zero stale VU bars left on screen. That run also caught a **regression this change had introduced**: trying 16 kHz and falling back on failure meant every device that refuses 16 kHz made PortAudio write ALSA errors straight to `stderr` — the very terminal ratatui draws on — and 5 devices' worth of that corrupted the popup (stale bars, rows stuck at 0%). `_pick_monitor_rate` now probes with `sd.check_input_settings` (`Pa_IsFormatSupported`, which opens nothing) and opens exactly once at a rate the device accepts: measured **9 ALSA stderr lines → 0**, all 5 devices still opening (44100/48000/48000/16000/16000). The no-failed-open property is pinned by `test_rate_is_probed_before_opening`. Pinned by `tests/shared/test_ratatui_mic_monitor.py` (18 tests, hermetic — `sounddevice` is faked, touches no hardware, uses no platform-divergent APIs, so every CI job runs it) and 6 Rust unit tests in `tui-rs/src/{ipc,mic_picker}.rs`. **Expected to work on macOS, unverified.** The code is deliberately platform-neutral (no `sys.platform` branch anywhere — the HAL ban is respected, and every call is plain PortAudio: `query_devices(int)`, `default_samplerate`, `InputStream(channels=1, samplerate, blocksize)` with the default float32 dtype), and macOS *is* reachable (`tui_available()` needs `socket.AF_UNIX`, which macOS has, and the flake builds `vt-tui` for `x86_64-darwin`/`aarch64-darwin`). No Mac was available to confirm it, so it ships on the strength of that reasoning rather than a test — the only macOS-specific hazard worth knowing is that a denied TCC mic permission fails every stream, which the per-device skip degrades to all-flat bars instead of an error, and nothing in the fix above is Linux-specific — `check_input_settings` is the same `Pa_IsFormatSupported` probe on CoreAudio and WASAPI. **WSL** uses the identical Linux path and is likewise untested on a WSL host, with one expected wrinkle: audio arrives via WSLg PulseAudio, which exposes essentially one real source (`RDPSource`), so every row will likely mirror the same level — mechanically correct, informationally near-useless there. **Native Windows is unreachable by design** — `tui_available()` returns False without `AF_UNIX` so the Rich TUI is used, and the whole `tui-rs` crate imports `std::os::unix` so it cannot even compile for Windows. Separate gap this exposed: **nothing in CI compiles or tests the Rust crate** (`cargo` is not in the flake's dev shell, `ci.yml` only runs pytest, and `rustPlatform.buildRustPackage` does not run `cargo test`), so a broken frontend build or a failed `vu` parse stays invisible until release. Add a `nix build .#vt-tui` step to the Linux CI job (cached, cheap) before trusting the Rust-side pins.

## Packaging / distribution gaps (end-user artifacts)

- [ ] **aarch64 Linux release build.** Only `x86_64-linux` is built today; `release.yml` names the asset `vt-x86_64.AppImage` so an arm job can attach later. Add a matrix job on an arm64 GitHub runner once `nixpkgs` `torch` builds for `aarch64-linux` (it is limited on arm); verify `nix build --system aarch64-linux .#default` under binfmt before wiring CI. The flake already lists `aarch64-linux` in `supportedSystems` and the runtime code is arch-neutral.
- [ ] **macOS packaging (`.app` / `.dmg`).** macOS is source-only (Nix or Homebrew) — there is no AppImage path (nix-appimage is Linux-only). Add a macOS runner + a bundler (PyInstaller onedir wrapped in a `.app`, or a Nix-based macOS bundler), then document it as the end-user macOS download.
- [ ] **CUDA-enabled AppImage / flake variant.** The bundled `torch` is CPU-only, so the AppImage ignores an NVIDIA GPU. Add a `packages.cuda` output (CUDA-enabled torch) with an explicit host-driver requirement, then document the choice. Until then the README states the AppImage is CPU-only.
- [ ] **FUSE-less AppImage UX.** Type-2 AppImages need FUSE 2; document `--appimage-extract-and-run` / `APPIMAGE_EXTRACT_AND_RUN=1` (done in README) and consider a runtime that self-extracts when `libfuse2` is absent, so a double-click works on FUSE-3-only distros.
- [ ] **Verify the AppImage model-bundle lookup on a real AppImage.** `src/model_download._local_model_source()` now also checks `dirname($APPIMAGE)/model-bundle` and `$APPDIR/model-bundle` (unit-tested in `tests/shared/test_model_download.py`), but the `$APPIMAGE`/`$APPDIR` values only exist inside a running AppImage — confirm on a built `vt-x86_64.AppImage` with a `model-bundle/` beside it.

- [ ] **The Bluetooth hands-free policy is now a loan rather than a permanent edit — but installs that already ran an older version stay stale.** `t2.apply_bluetooth_handsfree_policy` snapshots WirePlumber's `bluetooth.autoswitch-to-headset-profile` before its first change, registers an exit hook (`restore_bluetooth_autoswitch`) that puts the previous value back, and now *skips the policy entirely* when the current value cannot be read (nothing to restore ⇒ do not change it blind). Pinned by 5 tests in `tests/shared/test_config_sync.py` with `wpctl settings` faked. What it cannot repair: every install that ran a pre-change version left `false` permanently recorded (`~/.local/state/wireplumber/sm-settings`) and the app has no way to learn what the value was before it started. Those users reset it once by hand — `wpctl settings -s bluetooth.autoswitch-to-headset-profile true` (the WirePlumber default) — after which the snapshot/restore cycle keeps it honest. Consequence of the stale `false`: a Bluetooth headset will not auto-switch to its hands-free profile when an app opens its mic, so some apps see no microphone at all from a BT headset. Not verified against a real Bluetooth headset.

That run also caught a **regression this change had introduced**: trying 16 kHz and falling back on failure meant every device that refuses 16 kHz made PortAudio write ALSA errors straight to `stderr` — the very terminal ratatui draws on — and 5 devices' worth of that corrupted the popup (stale bars, rows stuck at 0%). `_pick_monitor_rate` now probes with `sd.check_input_settings` (`Pa_IsFormatSupported`, which opens nothing) and opens exactly once at a rate the device accepts: measured **9 ALSA stderr lines → 0**, all 5 devices still opening (44100/48000/48000/16000/16000). The no-failed-open property is pinned by `test_rate_is_probed_before_opening`. Pinned by `tests/shared/test_ratatui_mic_monitor.py` (18 tests, hermetic — `sounddevice` is faked, touches no hardware, uses no platform-divergent APIs, so every CI job runs it) and 6 Rust unit tests in `tui-rs/src/{ipc,mic_picker}.rs`. **Expected to work on macOS, unverified.** The code is deliberately platform-neutral (no `sys.platform` branch anywhere — the HAL ban is respected, and every call is plain PortAudio: `query_devices(int)`, `default_samplerate`, `InputStream(channels=1, samplerate, blocksize)` with the default float32 dtype), and macOS *is* reachable (`tui_available()` needs `socket.AF_UNIX`, which macOS has, and the flake builds `vt-tui` for `x86_64-darwin`/`aarch64-darwin`). No Mac was available to confirm it, so it ships on the strength of that reasoning rather than a test — the only macOS-specific hazard worth knowing is that a denied TCC mic permission fails every stream, which the per-device skip degrades to all-flat bars instead of an error, and nothing in the fix above is Linux-specific — `check_input_settings` is the same `Pa_IsFormatSupported` probe on CoreAudio and WASAPI. **WSL** uses the identical Linux path and is likewise untested on a WSL host, with one expected wrinkle: audio arrives via WSLg PulseAudio, which exposes essentially one real source (`RDPSource`), so every row will likely mirror the same level — mechanically correct, informationally near-useless there. **Native Windows is unreachable by design** — `tui_available()` returns False without `AF_UNIX` so the Rich TUI is used, and the whole `tui-rs` crate imports `std::os::unix` so it cannot even compile for Windows. Add a `nix build .#vt-tui` step to the Linux CI job (cached, cheap) before trusting the Rust-side pins.
